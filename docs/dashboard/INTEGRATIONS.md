# Provider integration status

Mailgun replaces the plan's Postmark adapter by the owner's subsequent instruction. The DNS/email task owns domain authentication, DNS and credential activation. Use `MAILGUN_DOMAIN=mg.p1landmanagement.com`, approved `EMAIL_FROM`, and secret `MAILGUN_API_KEY` on the worker. Initial owner-setup Mailgun delivery was verified; broader notification retry and delivery workflows still need acceptance. Do not put API keys in chat, source or build arguments.

QuickBooks is dormant by default. `P1_FEATURE_QUICKBOOKS` must equal the exact string `enabled` to mount its provider routes and webhook or enqueue/process reconciliation. Credentials alone never enable it. With the flag off, `/me` and Owner `/integrations` expose `features.quickbooks=false`, the latter omits its QuickBooks status, clients have no Billing route or billing-data access, and internal billing drafts remain available to granted staff. Existing connection records, encrypted credentials, migrations, provider code, and accounting data are retained. A previously queued reconciliation job is cancelled with `feature_disabled` without contacting Intuit. The dormant webhook acknowledges with 204 and ignores the body; SMS continues independently.

Staff with `revenue.billing` may mark a draft **Invoiced outside dashboard**, giving an optional reference, date, and note. This does not send, post, or pay an invoice. The mark is separate from the draft status, immutable except for a reasoned void, version/amount-checked against the draft reviewed by staff, idempotent by operation ID, and audited. One active mark is allowed per draft. A marked draft cannot be posted to QuickBooks even if the provider flag is later enabled; a draft with any existing posting request cannot be marked outside until finance resolves that ambiguous accounting outcome. Client Billing stays hidden while dormant; clients continue to see estimates on their property pages.

To activate QuickBooks later as a separate reviewed release: (1) configure `QBO_CLIENT_ID`, `QBO_CLIENT_SECRET`, `QBO_ENVIRONMENT`, `QBO_SERVICE_ITEM_ID`, `QBO_WEBHOOK_TOKEN`, and `INTEGRATION_ENCRYPTION_KEY` in the target environment; (2) set `P1_FEATURE_QUICKBOOKS=enabled`; (3) have the Owner connect in Settings → Integrations and run import preview; (4) complete the existing sandbox acceptance steps in [README.md](README.md) before production posting. Drafts marked outside the dashboard must **never** be posted. Whether to link those marks to matching imported QuickBooks invoices is a separate reviewed task.

When enabled, QuickBooks uses the configured redirect URI and sandbox environment by default. Owner-bound OAuth state is consumed transactionally; advisory locking serializes the initial company binding. Tokens are encrypted at rest and refresh is serialized. Review customer matches before importing; accounts without a mapping are excluded/quarantined.

Invoice posting uses stable request IDs and immutable payloads. Reconciliation rechecks customer ownership; imported invoices can move only to mapped clients, while local billing remains operationally attached and is hidden when accounting ownership differs. Accounting changes must originate in QuickBooks. Browser redirects never mark an invoice paid. Payment URLs are accepted only on approved Intuit hosts. Actual sandbox round trips, partial payments, credits, disconnection/retry and production eligibility must be verified before use.

Twilio needs authorized account/sender credentials, approved registration, signed callback URLs and recorded opt-in before activation. Consent and STOP/HELP callbacks are implemented; real deliverability and approval are pending. No outbound campaign or invoice-send action is automatic. Unknown email outcomes require explicit retry review to avoid duplicates.

Private object storage is Railway S3-compatible. Web service requires S3 endpoint, region, bucket, access key and secret. Images are decoded, oriented, size-limited and re-encoded as WebP to remove metadata. A synthetic bucket probe and 23 authenticated staging HTTP/S3 checks passed, including immutable retry, private/client boundaries, explicit publication and fixture deletion with HeadObject404. Physical-device capture, a general orphan cleanup policy and object recovery remain pending. Private files are served through authenticated access checks; signed direct-download URLs are not implemented yet.

Website inquiry bridging is implemented and has staging retry/idempotency evidence plus one synthetic production backend handoff with exactly one lead, receipt and audit. Public gateway/browser submission and owner acceptance remain separate gates. Retain one public intake system and propagate source IDs idempotently into dashboard leads.
