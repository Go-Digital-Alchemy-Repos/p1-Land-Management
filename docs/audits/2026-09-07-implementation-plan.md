# P1 website implementation plan

Historical proposal: see the [current master plan](../MASTER_PLAN.md), accepted CMS envelope and subsequent commercial initiative for current scope.

Status: PROPOSED. Based on the [September 7 review](./2026-09-07-website-review.md). This document plans work; no recommendation has been implemented or approved for production by its presence here.

## Objective and delivery principles

Increase qualified business inquiries and the proportion becoming booked assessments and profitable work. Default priority is balanced growth across existing services, pending owner preference. Retain the 1-acre positioning, existing useful content and current React/prerender architecture. Address acquisition failures before aesthetic experiments or new location-page volume.

Begin from refreshed `origin/main` (`5303da0` at review), preserving its newer slogan and separately accounting for existing uncommitted local changes. Use a dedicated `codex/` implementation branch/worktree with bounded ownership. Record the exact baseline again when work starts. Do not merge or reset the current dirty checkout wholesale.

Task lifecycle: PROPOSED → PLANNED → ASSIGNED → IN PROGRESS → IMPLEMENTED → REVIEW → INTEGRATION VALIDATION → ACCEPTED → DONE. Orchestrator owns integration and evidence; business owner supplies factual content/operational decisions. Implementation agents may not publish claims or alter production topology independently.

## Minimum interface and behavior decisions

- Add proposed `POST /api/leads`; request contains visitor/project details and bounded attribution fields. Response returns an opaque lead reference only after durable acceptance. Define generated OpenAPI/Zod/client types from the existing shared API workspace after A00 resolves hosting. No customer-data GET endpoint or new public admin UI in this scope.
- Server enforces contact-channel/location/project validation, payload bounds and abuse limits. Do not trust hidden inputs or client-only checks. Use a stable submission key for retries; duplicate acceptance must not create repeated notifications. Do not include submitted content in URLs, analytics or ordinary error logs.
- Persist receipt and notification state so temporary email failure does not lose an accepted lead. Prefer the approved existing CRM/storage if it provides these guarantees. If a new database is required, use additive schema and a reviewed migration/retention/backup plan; no existing customer-data migration assumed. Provider, spend, retention interval and receiving mailbox are explicit A00 decisions, not guesses.
- UI success promises receipt, not an unverified delivery/start time. Phone/email remain fallback. Operational response promises must match owner-confirmed staffing. Paid SMS, file uploads, automated estimates, customer accounts and new CRM UI are excluded from initial delivery.
- Keep the configured canonical origin `https://www.p1landmanagement.com`. Redirect apex to www and nonroot trailing slash / .html aliases to clean routes. Unknown URLs/assets return 404, with an accessible useful page for HTML requests. Canonical generation is shared between build and client.
- Maintain one stable business identity; page-specific Service/Article/Breadcrumb/FAQ nodes reference it as appropriate. Do not publish unsupported reviews, dates, addresses or credentials to fill schema fields.
- Introduce a small shared route/content metadata source used by prerender/sitemap/checks. Retain the existing framework; do not undertake an SSR-framework migration solely for SEO, since indexable prerendered HTML already works.

## Acceptance, measurement and rollout

| Gate | Required evidence |
|---|---|
| Lead safety/reliability | Accepted lead survives notification failure; delivery retry and alert tested; duplicate submission deduplicated; invalid/oversized/spam input handled; data retained in browser on recoverable error |
| Acquisition tracking | Campaign/landing information reaches permitted report; server acceptance is the conversion event; call click not mislabeled completed call; no PII analytics leakage |
| Search correctness | All 34 existing routes covered; new approved routes added to manifest; correct 200/redirect/404; unique title/description/canonical; no stale/duplicate page schema after navigation |
| Accessibility | Automated checks plus documented keyboard, VoiceOver, contrast, zoom/reflow, mobile controls and reduced-motion results; all critical form errors announced |
| Performance | Proposed mobile hero ≤250 KB, cards ≤100 KB, initial page assets ≤1.5 MB and initial JS ≤150 KB gzip; repeatable lab baseline/retest. Field p75 LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 when sufficient data exists |
| Security/runtime | Advisory results triaged for shipped versions; production server and minimal image verified; secrets absent from bundle/logs/build context; header policy tested; new endpoint threat boundary reviewed |
| Content | Owner-approved source and rights for every claimed project/testimonial; real dates, qualifications and pricing assumptions; no unpublished evidence treated as permission |
| Release | CI green; preview smoke; reviewed scoped diff; production publication authorized; exact revision reaches Railway success; live route/CTA/form acceptance smoke against approved test destination; rollback revision and owner recorded |

Use a 28-day baseline where practical, segmented by service, geography, source and device. At low volume use raw counts and lead-quality review rather than premature A/B tests. Set commercial lift targets only after validating the baseline and operational capacity; website traffic alone is not success. Track response time and booked/won outcomes so extra inquiries do not conceal poor fit or slow follow-up.

## Owner inputs and remaining validation

The implementation sequence is actionable, but vendor/topology activation and factual content publication need concrete A00/A03 inputs: preferred job mix, approved lead destination and account access, verified project/review assets, actual credentials/service boundaries, response capacity and retention requirements. Current default is balanced growth across listed services. Missing inputs block only their dependent tasks; static performance, metadata, QA and evidence inventory can progress independently.

Before closing the overall program, obtain account-backed indexing/Business Profile/lead evidence, repeat the unavailable PageSpeed/field check, complete the wider accessibility and dependency validations, and record each task's actual deployed outcome.
