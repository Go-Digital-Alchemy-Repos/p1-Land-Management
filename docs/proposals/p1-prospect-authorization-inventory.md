# Prospect linking authorization inventory and minimum release

Planning only. Inspected current dashboard route modules, SQL services, shared schema, dashboard UI and generated API surfaces. This refines the approved direction; no source/migration changes. Migration0011 still requires reservation; Core SSO0002 is a separate migration sequence.

## Initial release boundary

Only owner/manager/sales can create, search, review or link prospect organizations, contacts and properties through dedicated commercial context endpoints. Existing `/properties` and every operational API remain **operational-only for every role**, including owners. Prospects appear exclusively in the commercial sales panel for this first slice. This avoids prematurely granting dispatch assessment access or exposing prospects in financial/crew pickers. The same property UUID can later become operational through a separately reviewed onboarding gate.

Keep existing customers' property/client/contact IDs, response shapes, permissions and operational behavior. New context does not automatically create fees, messages, consent, appointments, portal accounts, grants, invoices, proposals or work. Generic customer creation remains explicitly available through its current workflow; commercial qualification must never call it.

## Shared guards to introduce under review

- Preserve `propertyAccess(actor,id)` semantics for existing operational data, adding an explicit property.lifecycle='operational' predicate in **all** role branches before client/crew checks. Return404 for prospect/unknown IDs. Do not add a general allowProspect flag to this commonly reused guard.
- Add a narrowly named commercial-context service that requires sales roles and retrieves only prospect-safe context DTOs. Linking an existing operational property requires normal property access plus sales role, but exposes no extra client portal permission.
- Mutations that bypass propertyAccess need `requireOperationalProperty(transaction,id)` using a row lock in the same transaction as the write; this checks lifecycle and nonnull real client. Use a consistent parent-before-child lock order across new/modified writers. Never rely on a UI filter or merely FK existence.
- Child-ID actions must resolve the child's actual property in SQL and assert operational scope; caller-supplied property IDs cannot override it. List SQL applies the same predicate, even if creation guards should make prospect child rows impossible. This protects imported/legacy/corrupt fixtures and future writers.
- Dedicated prospective contacts require client_id IS NULL for sales-context mutation. Customer-backed contact IDs may be linked with existing client-scoped access, but their name/channels remain edited only through the existing customer route. Relationships never grant access.

## DTO and caller inventory

- `lib/db/src/dashboard/schema.ts`: property.clientId and contact.clientId become nullable only under new lifecycle/type constraints. Do not propagate optionality blindly into operational DTOs.
- `artifacts/p1-dashboard/src/main.tsx` property selector and property/estimate/work form flows consume GET `/properties`; keep them operational-only with current client IDs. Do not add prospect rows to shared picker merely to support the commercial panel.
- `artifacts/p1-dashboard/src/CommercialInbox.tsx`: add a dedicated sales context panel and source/read-only intake view; use strict new DTOs with explicitly nullable email, client link and optional site. Search/create/link actions do not mutate an operational contact implicitly.
- `lib/api-spec/dashboard.openapi.json`, dashboard-generated client models under `lib/api-client-react/src/dashboard`: inspect/regenerate only affected schema routes. Current generated WorkOrder model expects property_id/name; retain it. New prospect DTO must be distinct from operational property responses rather than forcing existing consumers to accept prospect nulls.
- Existing SQL SELECT p.* / contact.* / lead.* can start leaking newly added private columns. Use explicit DTO selection for new sales data and preserve legacy output contracts; do not serialize organization roles/source/review metadata into general office/client responses.
- No separate property asset/map/search/export route module exists in the inspected API tree. Schema `property_asset` is present but there is no exposed asset API here. Future implementations must use the same boundary; do not claim unimplemented endpoints tested. Current property maps are client renderers of fetched property/area/work data and inherit API scope.

## Minimum implementation and acceptance gate

Release only organization/contact/property context linking, reviewed contact correction and read-only original intake. Reuse existing lead follow-up stage/owner actions. Include lifecycle and nullability constraints, link FK/indexes/versioning, explicit operation receipt fingerprinting, audit and all operational guards above in the same reviewed candidate. No prospect row is created until guarded code is deployed; feature flag is optional defense, not a replacement for authorization.

Test an operational customer fixture beside a sales-only prospect and intentionally create synthetic child rows under the prospect to prove list/detail/publish/mutation/worker defenses. For owner/manager/sales, only dedicated context routes expose prospect data; dispatch/finance/crew/client cannot list/read/update it through any legacy route. Operational customer behavior remains unchanged. Test phone-only correction, no intake changes, explicit reuse without automatic email/domain merge, stale version conflicts, operation replay/fingerprint conflicts, null-client constraints and no auth/client/access/QBO/outbox side effects. Include migration replay, restore rehearsal and direct-ID bypass regressions.

Assessment reports, prospect bookings, private prospect attachments, external proposal decisions, conversion/Won onboarding and new recurring work are subsequent gates. Those gates will deliberately expand selected lifecycle capabilities without relaxing the broad default operational boundary. No fee, marketing consent, outreach or portal grant is automated in this linking release.
