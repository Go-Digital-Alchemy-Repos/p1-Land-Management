## Staging baseline and release sequence

Before WP2, the website staging Railway hostname redirected HTTP 308 to production because the checked-in manifest names the canonical origin. WP2 adds an explicit `P1_WEBSITE_STAGING=enabled` server flag to make staging non-indexable and keep its own hostname. The first staging deployment (`04668a14-4d34-4ef3-b08f-10ddabd6a130`) uses validated prebuilt `dist`, `server`, and `config` in an equivalent runtime Dockerfile, because the full local source upload exceeded Railway's upload limit. It contains source revision `d8ca178c5f4b6d7b56bf396da23a4b1a476dee4c`; the Railway service's source configuration was not changed. The staging host now returns HTTP 200 without canonical redirect, `X-Robots-Tag: noindex, nofollow`, a live hero asset, and a homepage snapshot with `contentOverlayEnabled: true`.

Staging is a separate dataset from production. At the verified staging host, all 54 path snapshots returned HTTP 200. Of the 55 published component endpoints, **33 returned HTTP 200** and 22 returned HTTP 404. The 33 published payloads differ from current manifest defaults in 748 field values, listed with their published and default values in the JSON inventory. All 33 contain field keys unknown to the current manifest (688 unknown fields total), making them invalid under the existing all-or-nothing website validation. Consequently, the overlay-enabled website falls back to manifest defaults and shows no non-blog path-snapshot field differences; this does **not** mean staging has no published content. Five static blog paths remain projection-only for comparison.

The staging Core Postgres service was queried through Railway SSH using an explicit **read-only transaction**, returning only slugs and statuses. `cms_pages` had zero rows; legacy `blog_posts` had zero rows. The staging database has no `blog_publication_state` table, consistent with its older Core revision. No CMS-only page or blog post was observed in staging. This query read no content bodies and made no data changes. The website-side `/api/website/blog-publication` path returns 404 and was not used to infer this result. Non-blog public page routing is limited to manifest routes; dynamic blog article rendering uses a separate blog projection and does not depend on `P1_CMS_CONTENT_OVERLAY`. Thus pausing that overlay cannot remove a dynamic blog article.

After independent review of this inventory, staging `P1_CMS_CONTENT_OVERLAY` was set to `disabled`; `P1_WEBSITE_STAGING` remains `enabled`. Railway redeployment `597976de-d332-4c4c-8dff-283755c562d3` succeeded on 2026-09-23. On the actual staging hostname, all 54 manifest route snapshots returned HTTP 200 with `contentOverlayEnabled: false`, revision 0, and `X-Robots-Tag: noindex, nofollow`. Sampled Home, About, Contact, and Commercial Landscaping HTML pages returned HTTP 200 without redirect; `/healthz`, `/robots.txt` (`Disallow: /`), and `/opengraph.jpg` returned HTTP 200. Adding `cmsPreview=1` did not enable the overlay. The staging website still uses the validated prebuilt runtime image described above.

The staging homepage rendered the Owner-confirmed H1 “First Impressions Start at the Curb.” and contained the confirmed subheading “Commercial landscaping and exterior grounds maintenance that keep your property looking professional, welcoming, and well cared for.” WP2 did not edit either line.

Staging `/blog` and static blog article HTML returned HTTP 503 because its older Core lacks `/api/website/blog-publication` (previously observed HTTP 404). The website's blog renderer treats the absent publication projection as unavailable, independently of `P1_CMS_CONTENT_OVERLAY`. This is a staging integration limitation, not evidence that the pause removed blog content. No production variables or deployment changed in WP2. Production overlay must remain explicitly enabled until the same release as WP3 approved copy.

## Core staging compatibility gate

The isolated `website-staging` environment contains `p1-core-staging` and `p1-core-staging-db`, but no Dashboard service. A separate `dashboard-staging` environment has a Dashboard service; its current variable names do not include `CORE_MARKETING_ORIGIN` or `CORE_MARKETING_SERVICE_KEY`, which the CMS transport requires. A staging Dashboard CMS UI acceptance pass therefore needs deliberate non-production service integration before it can exercise this Core instance.

A read-only query of the staging Core database found Drizzle migration IDs 1–3 only, matching source migrations `0000_p1_foundation` through `0002_identity_federation` by SHA-256. The database was approximately 12 MB. Migrations `0003`–`0007` have not run: they add CMS concurrency columns, blog publication/revision/route/schedule/receipt tables, constraints, and immutability triggers. The newer Core starts by running pending migrations in production mode, so a healthy deployment would mutate this staging database automatically.

Before the attempted staging Core deployment, an owner-only custom-format `pg_dump` of this explicit database was saved outside the repository at `/Users/mikedickerman/.codex/backups/p1-wp2-staging/2026-09-23/core-staging-before-wp2.dump` (mode `0600`, 286,678 bytes). Its local SHA-256 matched the database-container SHA-256, `738c1ba86b2400d8a6886f85199d890c72029c23184c7821abff90aa5643b55e`; PostgreSQL 18 `pg_restore --list` read 366 lines. A restore would require a replacement staging database or coordinated downtime and reconciliation of subsequent writes. No restore was performed.

The source-built WP2 Core image was uploaded only to `p1-core-staging` as deployment `574b2ddd-bbb6-479f-af1f-bf3424426430`. Its build completed, but the container failed its production-mode configuration check before migrations: `P1_FORM_NOTIFICATION_RECIPIENTS` is missing from staging. No notification recipient was invented or configured. A subsequent read-only query still found exactly three applied migrations (IDs 1–3), and the prior staging Core deployment `78fa0eca-840e-4df7-bfaa-73ecf514ea32` remained running; its `/api/health/ready` returned HTTP 200 with the database connected. Therefore Core `GET /api/cms/status` and an authenticated CMS write returning 423 were **not** verified on staging. The WP2 Core write guards are validated locally. Dashboard staging has no configured Core marketing connection, so its CMS pause UI was also not exercised against staging Core.

No production variables or deployments changed in WP2. The production website's `P1_CMS_CONTENT_OVERLAY` variable was unset during this check; its current deployed code defaults to the overlay being enabled. A future production WP2 release must explicitly keep the flag enabled until WP3 copy releases in the same deployment as the overlay-off switch.
