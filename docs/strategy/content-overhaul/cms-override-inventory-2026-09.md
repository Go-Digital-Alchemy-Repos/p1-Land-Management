## Staging baseline and release sequence

Before WP2, the website staging Railway hostname redirected HTTP 308 to production because the checked-in manifest names the canonical origin. WP2 adds an explicit `P1_WEBSITE_STAGING=enabled` server flag to make staging non-indexable and keep its own hostname. The first staging deployment (`04668a14-4d34-4ef3-b08f-10ddabd6a130`) uses validated prebuilt `dist`, `server`, and `config` in an equivalent runtime Dockerfile, because the full local source upload exceeded Railway's upload limit. It contains source revision `d8ca178c5f4b6d7b56bf396da23a4b1a476dee4c`; the Railway service's source configuration was not changed. The staging host now returns HTTP 200 without canonical redirect, `X-Robots-Tag: noindex, nofollow`, a live hero asset, and a homepage snapshot with `contentOverlayEnabled: true`.

Staging is a separate dataset from production. At the verified staging host, all 54 path snapshots returned HTTP 200. Of the 55 published component endpoints, **33 returned HTTP 200** and 22 returned HTTP 404. The 33 published payloads differ from current manifest defaults in 748 field values, listed with their published and default values in the JSON inventory. All 33 contain field keys unknown to the current manifest (688 unknown fields total), making them invalid under the existing all-or-nothing website validation. Consequently, the overlay-enabled website falls back to manifest defaults and shows no non-blog path-snapshot field differences; this does **not** mean staging has no published content. Five static blog paths remain projection-only for comparison.

The staging Core Postgres service was queried through Railway SSH using an explicit **read-only transaction**, returning only slugs and statuses. `cms_pages` had zero rows; legacy `blog_posts` had zero rows. The staging database has no `blog_publication_state` table, consistent with its older Core revision. No CMS-only page or blog post was observed in staging. This query read no content bodies and made no data changes. The website-side `/api/website/blog-publication` path returns 404 and was not used to infer this result. Non-blog public page routing is limited to manifest routes; dynamic blog article rendering uses a separate blog projection and does not depend on `P1_CMS_CONTENT_OVERLAY`. Thus pausing that overlay cannot remove a dynamic blog article.

The staging flags remain `P1_CMS_CONTENT_OVERLAY=enabled` and `P1_WEBSITE_STAGING=enabled` pending independent review of this inventory. Only after the inventory gate is reviewed may staging change the overlay flag to disabled and verify source defaults, while Core staging has `P1_CMS_EDITING` paused. No production variables or deployment changed in WP2. Production overlay must remain explicitly enabled until the same release as WP3 approved copy.
