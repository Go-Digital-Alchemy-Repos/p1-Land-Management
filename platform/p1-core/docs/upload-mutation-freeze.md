# Temporary upload mutation freeze

The backwards-compatible hotfix is based on `f09e9d4199ffca634c0bc1df5c4e48d3c63bb762`. `UPLOAD_MUTATIONS_FROZEN=true` rejects new file mutations with HTTP503. The exact value `true` enables the guard; an absent flag preserves existing behavior. This change does not enable the flag, modify production configuration, or authorize deployment.

Guards cover shared CMS creation (including avatar and branding callers), generic attachments, career resumes, CMS replacement and CMS deletion. Defensive guards at R2 upload/delete run before configuration lookup and outside their error-to-null/false handlers. Shared-service and route guards run before local fallback paths or database mutations, so frozen R2 operations cannot silently become local files or delete a media row after a rejected object deletion. Reads and ordinary content editing remain available.

This is an admission guard, **not a distributed drain barrier**. Requests already past a guard can still finish. Before taking the final migration inventory, release operators must establish that all old writer replicas have been replaced or stopped, prior mutations have completed, and any ambiguous remote PUT outcomes are resolved. A rolling environment change or a successful health check alone does not establish those facts. Keep the freeze active through inventory, approved copy/revalidation, pointer reconciliation and candidate deployment/read verification. Recheck the inventory before unfreezing; never treat unidentified changes as successful migration.

Before candidate writes resume, rollback can retain copied objects and preserved originals while remaining frozen. After writes resume, candidate-created namespaced objects and their database references may not be readable by unmodified old code. A rollback must preserve these objects and use a separately verified namespace-compatible rollback artifact or approved reverse-copy/pointer reconciliation. Do not delete candidate objects or restore an old database snapshot as a substitute for preserving new records.

Tests use synthetic requests, mocked storage, and file-write/delete spies. They exercise mounted avatar/attachment/replace/delete handlers, shared CMS/resume services, defensive R2 behavior and unchanged normal uploads with the flag absent. No production storage or provider calls are used. The hotfix does not change old-main behavior for an ordinary unfrozen R2 failure; the broader candidate separately hardens production fallback.
