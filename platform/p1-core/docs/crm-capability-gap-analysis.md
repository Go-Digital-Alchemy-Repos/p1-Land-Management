## Important adaptation hazards

1. **Keep stable lifecycle semantics.** Core `updateCrmLead` interprets exactly `won` as client conversion. Changing display text is compatible; arbitrary stage IDs without a migration and terminal semantics are not. Never silently map all custom final stages to won.
2. **Settings permissions are distinct from daily CRM access.** Preserve current admin control of global settings and CRM editor access to records. New operational configuration should start admin-only unless the Orchestrator approves a narrower capability. Explicitly test disabled CRM and editor denial. Do not expose `crm_api_key` while building a configuration summary.
3. **Preserve isolation through deployment boundaries.** Source `tenantId` checks cannot simply be removed from copied functions and declared safe. Re-express record ownership and authenticated actor checks against Core's single-client instance. Do not add cross-client selectors or pooled client data.
4. **Source documentation is not sufficient proof.** Source `docs/deals-pipelines.md` describes blocking deletion of stages containing deals, but the inspected `deleteStage` service soft-deactivates non-system stages without checking deal count. Decide Core's archive/move policy explicitly and test historical records remain visible.
5. **Avoid hidden automation scope.** Campaign builders, marketing enrollment, external CRM integrations, contact/company relationship models and forecasting are discoverable source capabilities, but were not deeply validated here. Defer them to separately bounded design/assessment; no new marketing sends, client imports or external CRM writes are authorized by this report.

## Staged execution backlog and acceptance evidence

**CRM-0 — Confirm scope and contracts.** Accept this backlog, identify pilot-required features, and record CRM settings ownership plus data lifecycle. Keep the backup/form/worker/release fixes ahead of enhancements. Document migrations, defaults and rollback compatibility before persistent changes.

**CRM-1 — Settings foundation and pipeline presentation.** Add a discoverable CRM settings page using existing UI primitives, links to relevant current settings, and typed operational configuration. Allow labels/colors/order while preserving six stage keys. Acceptance: current board works with absent/invalid old settings; server rejects invalid/unknown keys; unauthorized/disabled-module access fails; save survives reload; won conversion and client uniqueness still pass; actual browser workflow validated.

**CRM-2 — Typed custom fields and explicit mapping.** Specify lead/client ownership, immutable keys, bounded values, archive behavior and conversion mapping; add definitions and per-form mapping preview. Acceptance: schema migration tested on populated data; archived values retained; existing heuristic intake remains compatible when mapping absent; malformed mapped input returns actionable errors; retries do not duplicate CRM effects; unknown fields cannot set owner/status/permissions; client instance export/restore includes new tables.

**CRM-3 — Follow-up usability.** Add worklist/filtering and agreed task metadata; only then enable reminders through the hardened worker mechanism. Acceptance: pagination and deterministic ordering on realistic synthetic volume; assignee validity and permission checks; duplicate/out-of-order notification processing; missed/retried reminders observable; browser verifies assignment, filtering and completion. Add versioned per-user profile layout preferences if useful without delaying pilot.

**CRM-4 — Advanced CRM design checkpoint.** Evaluate multiple pipelines, opportunities, activity history and note visibility against real client demand. This assessment is a later required decision point, not permission to silently omit capabilities or implement a second CRM architecture. Each selected capability receives its own contract, migration, access-control and performance acceptance plan.
